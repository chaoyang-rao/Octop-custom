# 小通与专家任务

小通可以把工作交给当前账号拥有、已启用的本地专家，包括后续新建的专家。执行者使用自己的模型、技能、连接器和工具配置；普通任务不要求 Codex、ACP 或 Git。

## 从原对话派工

直接向小通说明目标，例如：

> 让数据分析师检查这份表格的异常，给我结论和明细文件，结果回到这里。

小通通过 `expert_tasks` 查询实际专家、创建持久任务、读取状态。用户点名的专家优先；没有点名时按专家职责选择。派工工具返回任务编号后，后台执行继续运行，结果写回原会话，并显示实际执行专家的身份。

任务页也可手工创建普通任务并选择执行者。手工创建的任务会有自己的执行会话；从对话派出的任务额外保留来源会话。

派工不会自动复制附件或其他专家的工作区文件。涉及文件时，应提供执行专家有权访问的路径、连接器入口或必要内容；对话历史沿用现有按权限读取能力。

## 多专家任务群

同一目标交给第二位不同专家时，系统自动建立一个任务群，由小通主持；同一目标的后续派工和补充继续复用该群。只有一位执行专家时仍留在原对话。在已有团队群里派工时，复用当前群。

群里显示实际派工、每位专家公开回复、工具记录和阶段结果，以及小通的实际复核；发言使用真实专家的姓名和头像，工具详情沿用默认折叠。第一位专家在建群前已经完成的回复也会补入，不会为展示效果生成模拟讨论。原对话和任务详情提供群入口，结果继续回到原对话。

执行专家在该任务中咨询其他专家时，真实咨询对象也会加入参与者，提问和实际回复会作为执行记录进入群；不会把咨询内容变成用户的新要求。咨询执行会话负责答疑，后续正式派工由任务群或小通的原对话发起。

在任务群中补充要求，会关联当前目标供小通继续协调；不会因此自动扩大草稿 PR 的发布权限。工具审批仍在原执行会话处理，群内的执行链接可以打开待确认事项。删除群或群会话后不会自动重建，也不会删除专家已经完成的成果。

## 小通自动复核

同一用户需求派出的专家结果到齐并写回后，小通会自动核对原始目标，再记录明确决定：目标已完成、已安排不同的后续步骤，或需要用户补充一个具体信息。成员回复、网页和日志只作为资料，不能扩大原目标或开启未授权的自动 PR 发布。

任务页分别显示专家执行状态和主专家复核状态。需要补充时，在详情中的“补充并继续”填写真实输入；这段输入会进入原会话，不会由后台伪造用户发言。同一目标最多自动复核八轮，仍未收口时交由用户确认范围后继续；重启中断的主脑调用不会被静默重放。

“停止协调”会停止该目标的自动复核及尚未结束的成员任务，保留已产生的文件和验证记录。主专家已有的权限确认仍在原会话处理，补充输入不能绕过未完成的审批。

## 状态和恢复

- 同一工具调用重放不会重复派工；不同用户轮次可以正常创建不同任务。
- 小通在任务中创建子任务时，会等待真实子任务结果，协调等待不占用两个实际执行名额。
- 原会话正在回复或等待审批时，结果延后写入；刷新、断线和重启不会依赖临时 toast 保存结果。
- 审批在执行会话处理。多轮等待和最终结果分别回传；静默任务完成时刷新历史而不弹出成功通知。
- 取消会停止当前执行、验证和当前轮次的子任务。中断或失败后可明确重试，旧轮次的结果不能覆盖新轮次。

## 可选代码任务

在任务页选择“代码任务”，填写已登记的 Git 项目、基准版本和验证命令。此能力包含宿主机 Git 与验证进程，目前要求管理员身份，并遵守账号现有的工作区目录策略。

代码执行仍由选中的专家完成，其工具需要具备相应的项目访问能力。服务器创建独立 worktree，向该执行会话提供可信的项目目录；不会把原目录未提交的内容复制过去。基准版本默认 `HEAD`，即当前已提交版本。

验证命令按行填写，例如 `make all`、`npm test` 或 `uv run pytest`。支持带引号的参数，不执行管道、重定向或 Shell 组合语法。验证对应精确的 Git 文件树；验证过程或提交钩子改变代码时，需要检查后重新验证。日志、diff 和验证回执保存在任务自己的受管目录中。

默认保留本地修改与验证记录。开启“创建草稿 PR”后，服务器在验证通过后提交任务分支并交付 GitHub 草稿 PR；不自动合并。发布前再次检查任务轮次、取消状态和权限，已有 PR 会核验并复用。交付失败时保留本地目录，避免重复创建 PR。

代码任务的原目录、任务工作目录和专家自己的常规工作区是不同位置。任务页显示工作目录、验证状态和 PR 链接；后续工作应明确引用原任务及交付内容，避免把聊天回执当作已经完成的交付。

## 接口

- `POST /api/tasks`：保留普通任务字段，新增可选 `origin_thread_id` 与 `coding`。
- `coding`：`project_path`、`base_ref`、1～8 条 `test_commands`、默认关闭的 `publish_pr`。
- 任务列表与详情增加 `dispatch`，包含来源、父任务、代码交付和事件级回传状态，不返回内部请求去重键。
- `expert_tasks` 提供专家发现、创建、列表、分段读取、取消与重试；派工创建仅由账号主专家发起，用户也可在任务页手工创建。
- 自动复核中的 `expert_tasks decide` 由宿主上下文约束；任务详情的协调元数据记录决定、问题和轮次。
- `POST /api/tasks/{id}/coordination` 提交用户补充，`POST /api/tasks/{id}/coordination/stop` 停止该目标的后续协调。

本阶段通过聊天与任务页接收工作。GitHub Issue、评审和 CI 事件的自动监听属于后续接入层。
